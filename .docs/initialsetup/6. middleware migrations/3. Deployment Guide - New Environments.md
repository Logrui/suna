# Deployment Guide: Using This Solution in New Environments

**How to deploy the multi-domain Supabase solution to different infrastructure**

---

## Quick Start Checklist

For any new deployment:

1. **Identify your Supabase internal hostname**
2. **Set `NEXT_PUBLIC_SUPABASE_URL` in build environment**
3. **Ensure request headers are preserved** (Cloudflare does this automatically)
4. **Deploy - no code changes needed!**

---

## Deployment Scenarios

### Scenario 1: Local Development (Existing)

**Your Supabase:** `localhost:8888` (local machine)  
**Frontend:** `localhost:3000`  
**Backend:** `localhost:8000`

**Configuration:**
```env
# .env.local
NEXT_PUBLIC_SUPABASE_URL=http://localhost:8888
NEXT_PUBLIC_BACKEND_URL=http://localhost:8000/api
```

**Works on:** `http://localhost:3000` ✅

---

### Scenario 2: Docker Locally (Existing)

**Your Supabase:** `supabase-kong:8000` (Docker internal hostname)  
**Frontend:** Docker container  
**Backend:** Docker container  
**Access:** `localhost:3000` or `https://kortix.syhc.dev` via Cloudflare

**Configuration:**
```yaml
# docker-compose.yaml
frontend:
  build:
    args:
      NEXT_PUBLIC_SUPABASE_URL=http://supabase-kong:8000
      NEXT_PUBLIC_BACKEND_URL=http://backend:8000/api
  environment:
    NEXT_PUBLIC_SUPABASE_URL=http://supabase-kong:8000
    NEXT_PUBLIC_BACKEND_URL=http://backend:8000/api
```

**Works on:** `localhost:3000` AND `https://kortix.syhc.dev` ✅

---

### Scenario 3: Cloud Supabase (Migration)

**Your Supabase:** `project-name.supabase.co` (cloud)  
**Frontend:** Docker or Kubernetes  
**Backend:** Docker or Kubernetes  
**Access:** Custom domain via reverse proxy

**Configuration:**
```yaml
# Build args or environment
NEXT_PUBLIC_SUPABASE_URL=https://project-name.supabase.co
NEXT_PUBLIC_BACKEND_URL=https://api.yourdomain.com/backend
```

**How it works:**
- Browser sends relative requests to `/auth/v1/*`
- Proxy rewrites to `https://project-name.supabase.co/auth/v1/*`
- CORS configured in Supabase dashboard for your domain
- No code changes!

**CORS Configuration in Supabase:**
```
- http://localhost:3000
- https://yourdomain.com
- https://api.yourdomain.com
```

---

### Scenario 4: Self-Hosted Supabase

**Your Supabase:** Your own infrastructure  
**Frontend:** Docker on your network  
**Backend:** Docker on your network  
**Access:** Internal LAN or exposed via domain

**Configuration (Internal Network):**
```yaml
NEXT_PUBLIC_SUPABASE_URL=http://supabase.internal:8000
NEXT_PUBLIC_BACKEND_URL=http://backend.internal:8000/api
```

**Configuration (External Domain):**
```yaml
NEXT_PUBLIC_SUPABASE_URL=https://auth.yourdomain.com
NEXT_PUBLIC_BACKEND_URL=https://api.yourdomain.com
```

**Network Requirements:**
- Frontend ↔ Supabase can communicate
- Docker internal DNS or static hostnames
- No firewall blocking internal traffic

---

### Scenario 5: Kubernetes Deployment

**Your Supabase:** Kubernetes service  
**Frontend:** Kubernetes deployment  
**Backend:** Kubernetes service  
**Access:** Ingress controller

**Configuration (In-Cluster):**
```yaml
# In build args
NEXT_PUBLIC_SUPABASE_URL=http://supabase.default.svc.cluster.local:8000
NEXT_PUBLIC_BACKEND_URL=http://backend.default.svc.cluster.local:8000/api
```

**How Kubernetes DNS works:**
- Automatic service discovery: `service-name.namespace.svc.cluster.local`
- No hardcoding IPs needed
- Survives pod restarts

**Ingress Configuration:**
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend
spec:
  ingressClassName: nginx
  rules:
  - host: yourdomain.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend
            port:
              number: 3000
```

**Works on:** `https://yourdomain.com` ✅  
**Automatic:** Runtime URL detection handles everything

## Step-by-Step: Deploy to New Environment

### Step 1: Identify Your Supabase URL

**Questions to answer:**
- [ ] Where does Supabase run? (cloud/self-hosted/docker)
- [ ] What's the internal hostname? (if running on your infrastructure)
- [ ] Can the frontend service reach it?
- [ ] What ports are exposed?

**Examples:**
```
Cloud Supabase:         https://abc123.supabase.co
Docker on same machine: http://supabase-kong:8000
Kubernetes:             http://supabase.default.svc.cluster.local:8000
Self-hosted:            http://supabase.internal.company.com:8000
```

### Step 2: Identify Your Backend URL

**Questions to answer:**
- [ ] Where does the backend service run?
- [ ] What's the internal hostname/IP?
- [ ] What port?
- [ ] What path prefix? (usually `/api`)

**Examples:**
```
Docker on same machine: http://backend:8000/api
Kubernetes:             http://backend.default.svc.cluster.local:8000/api
Self-hosted:            http://backend.internal.company.com:8000/api
```

### Step 3: Set Build Environment Variables

**For Docker builds:**
```yaml
# docker-compose.yaml or Dockerfile
docker build \
  --build-arg NEXT_PUBLIC_SUPABASE_URL=http://supabase-kong:8000 \
  --build-arg NEXT_PUBLIC_BACKEND_URL=http://backend:8000/api \
  -t my-frontend:latest \
  .
```

**For Kubernetes:**
```yaml
# values.yaml or ConfigMap
env:
  - name: NEXT_PUBLIC_SUPABASE_URL
    value: http://supabase.default.svc.cluster.local:8000
  - name: NEXT_PUBLIC_BACKEND_URL
    value: http://backend.default.svc.cluster.local:8000/api
```

**For CI/CD (GitHub Actions):**
```yaml
- name: Build Docker image
  env:
    SUPABASE_URL: ${{ secrets.SUPABASE_URL }}
    BACKEND_URL: ${{ secrets.BACKEND_URL }}
  run: |
    docker build \
      --build-arg NEXT_PUBLIC_SUPABASE_URL=$SUPABASE_URL \
      --build-arg NEXT_PUBLIC_BACKEND_URL=$BACKEND_URL \
      -t my-frontend:${{ github.sha }} \
      .
```

### Step 4: Configure Request Header Preservation

**If using reverse proxy:**
- ✅ Cloudflare Tunnel: Already preserves headers (automatic)
- ✅ Nginx: Configure to pass headers
- ✅ HAProxy: Configure to pass headers
- ✅ Kubernetes Ingress: Automatic

**Nginx example:**
```nginx
location / {
    proxy_pass http://frontend:3000;
    
    # Preserve original request info
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host $server_name;
}
```

### Step 5: Deploy and Test

**After deployment:**

1. **Test direct access:**
   ```bash
   # If deploying to domain
   curl https://yourdomain.com
   # Should return HTML
   ```

2. **Test authentication:**
   - Visit your domain
   - Try to login
   - Check browser console for errors
   - Check auth cookies are set for your domain

3. **Test data fetching:**
   - After login, visit dashboard
   - Data should load
   - Check Network tab for `/auth/v1/*` relative requests

4. **Test Cloudflare Tunnel (if applicable):**
   - Visit your tunnel domain
   - Repeat auth tests
   - Should work identically to direct access

## Troubleshooting New Deployments

### Problem: Auth returns 400 errors

**Likely causes:**
1. Wrong `NEXT_PUBLIC_SUPABASE_URL` in build
2. Supabase not reachable from container
3. CORS not configured in Supabase

**Solutions:**
```bash
# Check URL is correct
docker exec frontend env | grep NEXT_PUBLIC_SUPABASE_URL

# Test connectivity from container
docker exec frontend curl http://supabase-kong:8000/health

# Check CORS in Supabase dashboard if cloud
```

### Problem: Cookies not being set

**Likely causes:**
1. Request headers not preserved through proxy
2. Same-origin not working (domain mismatch)
3. Secure/HttpOnly flags blocking cookies

**Solutions:**
```bash
# Check headers in Network tab
# Should see x-forwarded-host, x-forwarded-proto

# Verify domain in Set-Cookie header
# Should match your domain

# Test middleware sees correct host
# Add logging to middleware.ts
```

### Problem: Works locally, fails in production

**Likely causes:**
1. Different Supabase URL between environments
2. HTTPS/HTTP mismatch
3. DNS resolution issue

**Solutions:**
```bash
# Verify env vars in production
docker inspect your-container | grep NEXT_PUBLIC_SUPABASE_URL

# Test DNS resolution
nslookup supabase-kong
# Should return an IP

# Check protocol mismatch
# x-forwarded-proto should be https if using HTTPS
```

## Environment Variable Reference

### Required Variables

| Variable | Purpose | Example |
|----------|---------|---------|
| `NEXT_PUBLIC_SUPABASE_URL` | Internal Supabase URL for rewrites | `http://supabase-kong:8000` |
| `NEXT_PUBLIC_BACKEND_URL` | Backend API URL for rewrites | `http://backend:8000/api` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Public Supabase API key | `eyJhbGc...` |

### Optional Variables

| Variable | Purpose | Example |
|----------|---------|---------|
| `NEXT_PUBLIC_ENV_MODE` | Environment mode | `local` or `production` |
| `NEXT_OUTPUT` | Next.js output format | `standalone` |

### Build-Only Variables

These are needed **during Docker build**, not at runtime:

```dockerfile
ARG NEXT_PUBLIC_SUPABASE_URL=http://supabase-kong:8000
ARG NEXT_PUBLIC_BACKEND_URL=http://backend:8000/api
ARG NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGc...
```
