# Quick Reference: Multi-Domain Deployment

**TL;DR** - How the fix enables localhost + Cloudflare simultaneously

---

## 🎯 The Problem (What Was Broken)

| Access Method | Status | Error |
|---------------|--------|-------|
| `localhost:3000` | ✅ Working | — |
| `kortix.syhc.dev` | ❌ Broken | `auth/v1/* - 400 Bad Request` |

**Why:** Supabase URL was hardcoded at build time, different between local and Docker

---

## ✅ The Solution (What We Fixed)

### **Three-Layer URL Detection**

```
┌─────────────────────────────────────────┐
│ Layer 3: Middleware                     │
│ Uses: Request headers (host, protocol)  │
│ For: Route protection & auth checks     │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│ Layer 2: Server Client                  │
│ Uses: Request headers (x-forwarded-*)   │
│ For: Server-side data fetching          │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│ Layer 1: Browser Client                 │
│ Uses: window.location.origin            │
│ For: Client-side auth & data            │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│ Browser makes relative URLs             │
│ /auth/v1/token → (current domain)       │
└─────────────────────────────────────────┘
```

---

## 📊 How It Works

### **Localhost Flow**

```
localhost:3000
    ↓
Browser client detects: window.location.origin = "http://localhost:3000"
    ↓
Browser requests: /auth/v1/token
    ↓
Next.js rewrites (from .env.local): → http://localhost:8888/auth/v1/token
    ↓
✅ Works! Cookies set for localhost:3000
```

### **Cloudflare Tunnel Flow**

```
kortix.syhc.dev
    ↓
Cloudflare Tunnel routes to: localhost:3000
    ↓
Browser client detects: window.location.origin = "https://kortix.syhc.dev"
    ↓
Browser requests: /auth/v1/token
    ↓
Next.js rewrites (from docker build): → http://supabase-kong:8000/auth/v1/token
    ↓
Docker routing: supabase-kong:8000 (internal hostname)
    ↓
✅ Works! Cookies set for kortix.syhc.dev
```

## 💡 Key Principles

| Principle | Why | Where |
|-----------|-----|-------|
| **Build-time env vars for stable hostnames** | Docker internal hostnames don't change | `next.config.ts` rewrites |
| **Runtime detection for client-facing URLs** | Browser origin unknown at build time | Browser & server clients |
| **Same-origin requests by default** | Cookies work, no CORS issues | Browser → `/auth/v1/*` |
| **Request headers preserve original info** | Middleware needs to know where request came from | Server/middleware |

## 🚀 Deployment Quick Start

1. **Set environment variables for your deployment:**
   ```yaml
   NEXT_PUBLIC_SUPABASE_URL=<your-supabase-internal-url>
   NEXT_PUBLIC_BACKEND_URL=<your-backend-url>
   ```

2. **Build Docker image (rewrites baked in)**
   ```bash
   docker build -t my-app --build-arg NEXT_PUBLIC_SUPABASE_URL=...
   ```

3. **Deploy to any domain**
   - Runtime detection handles the rest
   - No rebuild needed for new domains!

## ❓ FAQ

**Q: Why does the browser use relative URLs?**  
A: Same-origin requests ensure cookies work correctly without CORS issues.

**Q: Why set `NEXT_PUBLIC_SUPABASE_URL` at build time?**  
A: For server-to-Supabase rewrites. Browser doesn't use this env var directly.

**Q: Can I add a new domain without rebuilding?**  
A: Yes! Runtime detection handles new domains automatically. Just route traffic to your app.

**Q: What if my Supabase is in the cloud?**  
A: Set `NEXT_PUBLIC_SUPABASE_URL=https://project.supabase.co` at build time, same principle applies.

**Q: Does this work with self-hosted Supabase?**  
A: Yes! Set the appropriate internal hostname for your deployment context.

## 📞 Troubleshooting

| Problem | Solution |
|---------|----------|
| 400 errors from Supabase | Check `NEXT_PUBLIC_SUPABASE_URL` in docker-compose.yaml |
| Auth cookies not set | Verify browser requests are relative URLs (`/auth/v1/*`) |
| Works on localhost, not Cloudflare | Rebuild Docker image with `x-forwarded-proto` support |
| Server-side auth fails | Check middleware has access to request headers |
