# Backend API Proxy Fix - Relative URLs

**Date:** October 29, 2025  
**Status:** 🔧 **IN PROGRESS**  
**Purpose:** Fix browser DNS resolution errors by using relative URLs for backend API calls

---

## 🔴 Problem Summary

After successfully implementing OAuth with dynamic URL detection, we encountered a critical issue:

### **Browser Console Errors:**
```
GET http://backend:8000/api/agents?limit=100&sort_by=name&sort_order=asc net::ERR_NAME_NOT_RESOLVED
GET http://backend:8000/api/templates/kortix-all net::ERR_NAME_NOT_RESOLVED
```

### **Root Cause:**
- Frontend code was making direct requests to `http://backend:8000/...` from the browser
- `backend` is a Docker **internal hostname** that browsers cannot resolve
- Only Docker containers can communicate using internal hostnames
- Browser needs to use public URLs or relative paths

### **Impact:**
1. **Cloudflare Tunnel (`https://kortix.syhc.dev`)**: Login succeeds, but dashboard fails to load data
2. **Localhost (`http://localhost:3000`)**: Login succeeds, account info loads, but agents/chats/data fail to load

---

## ✅ Solution: Use Relative URLs Everywhere

### **Architecture:**

```
┌─────────────────────────────────────────────────────────────┐
│ Browser (User)                                              │
│ https://kortix.syhc.dev OR http://localhost:3000           │
└────────────────────┬────────────────────────────────────────┘
                     │
                     │ GET /api/agents
                     │ (Relative URL - same origin)
                     ▼
┌─────────────────────────────────────────────────────────────┐
│ Next.js Frontend                                            │
│ • Receives browser request for /api/agents                  │
│ • next.config.ts rewrites intercept                         │
│ • Proxies to: http://backend:8000/api/agents               │
│   (Server-side - can use Docker hostname)                   │
└────────────────────┬────────────────────────────────────────┘
                     │
                     │ Proxy (server-side)
                     ▼
┌─────────────────────────────────────────────────────────────┐
│ Backend API (Docker)                                        │
│ http://backend:8000                                         │
│ • Receives proxied request                                  │
│ • Returns data                                              │
└─────────────────────────────────────────────────────────────┘
```

### **Key Principle:**
- **Browser requests**: Use relative URLs (`/api/*`) or current origin (`${window.location.origin}/api/*`)
- **Server-side requests**: Use Docker internal hostnames (`http://backend:8000`)
- **Next.js rewrites**: Proxy `/api/*` to `http://backend:8000/api/*` (already configured ✅)

## 🛠️ Implementation Steps

### **Step 1: Create Centralized API URL Utility**

**File:** `frontend/src/lib/get-api-url.ts`

```typescript
/**
 * Get the correct API URL based on execution context
 * 
 * Browser (client-side):
 *   - Uses window.location.origin + '/api'
 *   - Results in relative URLs like: /api/agents
 *   - Next.js rewrites proxy to backend
 * 
 * Server (SSR/middleware):
 *   - Uses environment variable
 *   - Direct Docker communication: http://backend:8000/api
 */
export const getApiUrl = () => {
  if (typeof window !== 'undefined') {
    // Browser: use current origin + /api (Next.js will proxy)
    return `${window.location.origin}/api`;
  }
  // Server: use environment variable (for Docker internal communication)
  return process.env.NEXT_PUBLIC_BACKEND_URL || 'http://backend:8000/api';
};
```

### **Step 3: Pattern to Replace**

**OLD (Direct environment variable):**
```typescript
const API_URL = process.env.NEXT_PUBLIC_BACKEND_URL || '';
```

**NEW (Dynamic URL detection):**
```typescript
import { getApiUrl } from '@/lib/get-api-url';
const API_URL = getApiUrl();
```

**For inline usage:**
```typescript
// OLD
const url = `${process.env.NEXT_PUBLIC_BACKEND_URL}/sandboxes/${sandboxId}/files/content`;

// NEW
const url = `${getApiUrl()}/sandboxes/${sandboxId}/files/content`;
```

### **Step 4: Docker Environment Variables (Keep As Is)**

**`docker-compose.yaml`:**
```yaml
frontend:
  environment:
    - NEXT_PUBLIC_BACKEND_URL=http://backend:8000/api  # For SSR only
```

**`.env.local`:**
```bash
NEXT_PUBLIC_BACKEND_URL=http://localhost:8000/api  # For SSR only
```

**Note:** These are used for server-side requests only. Browser requests will use relative URLs.

## 📝 Code Quality Notes

### **Why This Approach:**
1. **Single Source of Truth**: `getApiUrl()` centralizes URL logic
2. **Works Everywhere**: Browser and server contexts handled correctly
3. **No Hardcoding**: Adapts to any domain automatically
4. **Follows OAuth Pattern**: Same strategy that fixed OAuth issues
5. **Type Safety**: Can be enhanced with TypeScript if needed

### **Alternative Considered (Rejected):**
- Updating environment variables per deployment → Creates same domain-locking issue
- Using multiple environment variables → Increases complexity and maintenance
