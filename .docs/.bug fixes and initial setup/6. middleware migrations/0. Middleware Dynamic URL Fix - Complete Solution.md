# Middleware Dynamic URL Fix - Complete Solution ✅

**Date:** October 31, 2025  
**Status:** ✅ **WORKING** - Simultaneous localhost + Cloudflare Tunnel access confirmed  
**Problem:** Frontend could access localhost but failed on Cloudflare Tunnel with Supabase 400 errors  
**Solution:** Dynamic URL detection through middleware + runtime environment variables

---

## 🎯 Executive Summary

Successfully fixed the issue where `https://kortix.syhc.dev` was returning Supabase 400 errors while `localhost:3000` worked perfectly.

**Root Cause:** Supabase URL was hardcoded at **build time** in `next.config.ts`, creating a mismatch between local dev and Cloudflare deployments.

**Solution:** Implement **runtime-based URL detection** throughout the stack:
- Browser client: Uses `window.location.origin`
- Server client: Uses request headers (`host`, `x-forwarded-proto`)
- Middleware: Uses request headers for auth checks
- Docker environment: Uses internal Docker hostname (`supabase-kong:8000`)
- Local development: Uses localhost URL (`localhost:8888`)

**Result:** ✅ Same Docker image works on both `localhost:3000` AND `https://kortix.syhc.dev`

## 🔴 The Problem

### **Error Log (Cloudflare Tunnel)**
```
auth/v1/token - 400 Bad Request
auth/v1/user - 400 Bad Request  
rest/v1/rpc/get_accounts - 400 Bad Request

Error: Unexpected token 'B', "Bad request" is not valid JSON
```

### **Why It Happened**

**Build-time Configuration (next.config.ts):**
```typescript
// WRONG: This is evaluated at BUILD time
const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL || 'http://localhost:8888';

// This URL gets hardcoded into the Docker image FOREVER
{
  source: '/auth/v1/:path*',
  destination: `${supabaseUrl}/auth/v1/:path*`,  // Frozen here!
}
```

**What Happened:**
1. Docker image built with `.env` setting `NEXT_PUBLIC_SUPABASE_URL=http://supabase-kong:8000`
2. Next.js compiled rewrites with `supabaseUrl = 'http://supabase-kong:8000'`
3. When accessed via Cloudflare Tunnel, browser tried to reach `/auth/v1/*`
4. Next.js rewrote to `http://supabase-kong:8000/...` 
5. **But from Cloudflare context, `supabase-kong` doesn't exist!**
6. Kong returned `400 Bad Request` (with plain text, not JSON)
7. Supabase client couldn't parse response → Auth failed

## ✅ The Solution

### **1. Restore Build-Time Rewrites**

**`frontend/next.config.ts`:**
```typescript
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  output: (process.env.NEXT_OUTPUT as 'standalone') || undefined,
  
  async rewrites() {
    // Use environment variables set at build time
    // Docker: NEXT_PUBLIC_SUPABASE_URL=http://supabase-kong:8000
    // Local: NEXT_PUBLIC_SUPABASE_URL=http://localhost:8888
    const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL || 'http://localhost:8888'
    const backendUrl = process.env.NEXT_PUBLIC_BACKEND_URL || 'http://backend:8000/api'
    
    return [
      // Backend API proxy
      {
        source: '/api/:path*',
        destination: `${backendUrl}/:path*`,
      },
      
      // Supabase Auth proxy
      {
        source: '/auth/v1/:path*',
        destination: `${supabaseUrl}/auth/v1/:path*`,
      },
      {
        source: '/rest/v1/:path*',
        destination: `${supabaseUrl}/rest/v1/:path*`,
      },
      {
        source: '/storage/v1/:path*',
        destination: `${supabaseUrl}/storage/v1/:path*`,
      },
      {
        source: '/realtime/v1/:path*',
        destination: `${supabaseUrl}/realtime/v1/:path*`,
      },
      
      // PostHog analytics
      {
        source: '/ingest/static/:path*',
        destination: 'https://eu-assets.i.posthog.com/static/:path*',
      },
      {
        source: '/ingest/:path*',
        destination: 'https://eu.i.posthog.com/:path*',
      },
      {
        source: '/ingest/flags',
        destination: 'https://eu.i.posthog.com/flags',
      },
    ]
  },
  skipTrailingSlashRedirect: true,
}

export default nextConfig
```

**Key Points:**
- Rewrites use `process.env.NEXT_PUBLIC_SUPABASE_URL` from build time
- Docker build sets it to `http://supabase-kong:8000` (internal Docker network)
- Local dev `.env.local` sets it to `http://localhost:8888` (local Supabase)
- Rewrites are fixed per build, which is correct!

```typescript
import { createBrowserClient } from '@supabase/ssr'

export function createClient() {
  // Dynamic: Uses current browser origin
  const supabaseUrl = typeof window !== 'undefined' 
    ? window.location.origin 
    : 'http://localhost:3000'
  
  return createBrowserClient(
    supabaseUrl,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      isSingleton: true,
    }
  )
}
```

**Why This Works:**
- Browser always requests `/auth/v1/*` (relative URL)
- Request goes to the **current domain** (`localhost:3000` or `kortix.syhc.dev`)
- Next.js rewrites it server-side to the actual Supabase
- Same-origin requests = cookies work correctly

### **3. Server Client (Already Working)**

**`frontend/src/lib/supabase/server.ts`:**
```typescript
'use server'
import { createServerClient } from '@supabase/ssr'
import { cookies, headers } from 'next/headers'

export async function createClient() {
  const cookieStore = await cookies()
  const headerStore = await headers()

  // Dynamic: Detects current request origin
  const origin = headerStore.get('x-forwarded-host') || headerStore.get('host')
  const protocol = headerStore.get('x-forwarded-proto') || 'http'
  const supabaseUrl = origin ? `${protocol}://${origin}` : process.env.NEXT_PUBLIC_SUPABASE_URL!

  return createServerClient(
    supabaseUrl,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll()
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) =>
              cookieStore.set(name, value, options)
            )
          } catch {
            // Ignored in Server Components
          }
        },
      },
    }
  )
}
```

**Why This Works:**
- Reads `host` and `x-forwarded-proto` from incoming request headers
- Cloudflare Tunnel sets `x-forwarded-proto: https` and `x-forwarded-host: kortix.syhc.dev`
- Server automatically uses the correct origin
- Falls back to environment variable if headers missing

### **4. Middleware (Already Working)**

**`frontend/src/middleware.ts`:**
```typescript
export async function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;
  
  // Skip static files and API routes
  if (
    pathname.startsWith('/_next') ||
    pathname.startsWith('/favicon') ||
    pathname.includes('.') ||
    pathname.startsWith('/api/')
  ) {
    return NextResponse.next();
  }

  // ... allow public routes ...

  // For protected routes, create Supabase client
  const host = request.headers.get('host') || 'localhost:3000'
  const protocol = request.headers.get('x-forwarded-proto') || 'http'
  const supabaseUrl = `${protocol}://${host}`

  const supabase = createServerClient(
    supabaseUrl,  // Dynamic URL from request
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll();
        },
        setAll(cookiesToSet) {
          // Handle cookies...
        },
      },
    }
  )

  // Auth check uses dynamic Supabase URL
  const { data: { user }, error: authError } = await supabase.auth.getUser()
  
  if (authError || !user) {
    // Redirect to auth
    const url = request.nextUrl.clone()
    url.pathname = '/auth'
    return NextResponse.redirect(url)
  }

  return supabaseResponse
}
```

**Why This Works:**
- Middleware runs for every request, has access to headers
- Detects origin from `host` + `x-forwarded-proto` headers
- Creates Supabase client with correct origin
- Auth checks work on both localhost and Cloudflare

## 🔑 Key Insights

### **1. Build-Time Rewrites Are Correct**
Don't try to make rewrites dynamic - they're **supposed to be hardcoded per build**. Instead:
- Docker builds with `supabase-kong:8000` (internal)
- Local dev uses `localhost:8888` (local machine)
- This is the correct approach!

### **2. Runtime URL Detection Happens Elsewhere**
The **browser client** and **server client** use runtime detection:
- Browser: `window.location.origin`
- Server: request headers
- This is where dynamic URL detection belongs

### **3. Same-Origin Requests Are Key**
By having the browser request relative URLs `/auth/v1/*`:
- Requests go to the same origin as the page
- Cookies work correctly (same-origin policy)
- No cross-origin issues
- Works from any domain automatically!

### **4. Network Configuration Matters**
- Local dev: All services on host machine (`localhost`)
- Docker: Services on Docker internal network (`service-name:port`)
- Cloudflare: Traffic routes through tunnel to Docker network
- Each context uses the appropriate hostname!

## 🎓 Lessons Learned

1. **Build-time constants are fine for stable hostnames**
   - Docker internal hostnames don't change per deployment
   - Build once, deploy anywhere with correct environment setup

2. **Runtime detection is for client-facing URLs**
   - Browser can't know its origin until request time
   - Use `window.location.origin` for browser clients
   - Use request headers for server clients

3. **Headers are your friend**
   - `x-forwarded-host`, `x-forwarded-proto` preserve original request info
   - Cloudflare Tunnel sets these automatically
   - Middleware has access to them for dynamic behavior

4. **Same-origin requests solve most CORS problems**
   - Relative URLs (`/auth/v1/*`) are always same-origin
   - Cookies work correctly
   - Much simpler than trying to handle cross-origin auth
